# DKMS 0.1.1 post-soak validation

## Environment

- Host: Raspberry Pi 4
- Kernel: `6.12.47+rpt-rpi-v8`
- Primary radio: RTL8812AU using `rtw_8812au`
- Experimental peer: RTL8192FU using `rtl8xxxu`
- Mesh: open 802.11s, channel 1, HT20

## Production soak

The run began at 15:29 CEST and was stopped on request at 20:00 CEST. The
harness produced a normal summary:

- established states: 337/337;
- directional ping batches: 672/672;
- checksummed transfers: 10/10;
- recovery windows and invalidations: zero;
- kernel USB transport events: zero;
- temperature range: 75.958--80.828 C.

## DKMS activation

DKMS 0.1.1 built against the running kernel and installed all five modules.
The loaded `srcversion` values matched the corresponding build artifacts.
Automatic userspace recovery restored the mesh in five seconds. Both immediate
10-packet directional ping runs passed without a kernel warning or USB error.

## Multicast localization

Twenty 20-packet rounds in both directions captured every frame at its sender:

- RTL8812AU sender: 400; peer receiver: 399;
- RTL8192FU sender: 400; RTL8812AU receiver: 398.

The three losses occurred after sender capture and were bidirectional. No USB
transport event occurred. Because 802.11 multicast is unacknowledged and the
peer uses an experimental driver, this result does not isolate a defect to the
RTL8812AU path. Repeat with two stable RTL8812AU radios.

## Transfer integrity

The final-build gate transferred the same 512 MiB random payload both ways:

- RTL8812AU to peer: SHA-256 match, 8,765,407 B/s;
- peer to RTL8812AU: SHA-256 match, 6,335,195 B/s.

Both HWMP path tables remained populated and no USB transport event was logged.
The first attempt identified an HTTP-server readiness race before transferring
any bytes. The harness now proves both endpoints reachable before measurement.
It also prevents namespace HTTP servers from inheriting the test lock and waits
for their cleanup. A follow-up 1 MiB smoke passed and left no server or lock.

## Read-only control retry

The test-only kretprobe filter casts the narrow `usb_control_msg()` request,
request-type, and value arguments to their API widths before comparison. This
is required on ARM64 because upper register bits for narrow arguments are not
part of their values.

A debugfs byte read of register `0x5a7` produced:

```text
read register 0x5a7 recovered after 2 attempts, retries=1
control injector removed, remaining=0 matching_calls=2 missed=0
```

The injector requires request type `0xc0`, so successful writes are outside its
target predicate. The peer remained established and both post-injection
10-packet directional ping runs passed.
